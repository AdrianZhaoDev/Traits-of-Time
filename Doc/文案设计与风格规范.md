# 文案设计与风格规范

全项目视觉采用已批准的 **A「爆笑开播」**，唯一依据为 [UI 整体风格方案](./UI整体风格方案.md)，表现节奏见 [动效与微交互规范](./动效与微交互制作规范.md)，实际 Canvas 实施与验证状态见 [README](../README.md#本轮实际验证)。换肤不授权改动生产文案、玩法或素材。明亮、荒诞的呈现不要求每句都搞笑；正文仍以自然中文、真实因果和阅读为先。

正式游戏名为「穿越了这次我带大喇叭逆袭」，不得截断或另造简称。红色喇叭只是品牌识别，不是人人固定携带的开局家当；文案不能新增这件物品、奖励或能力。

## 一、优先级：先顺口，再精简

用现代、自然、通俗的中文讲明代故事。参考《人生重开模拟器》的轻松、直接和容易扫读，不模仿具体句子，不把每条事件都写成段子。

**先像正常人说话，再删废话；宁可多几个字，也不要读着磕绊。**

- 让玩家一遍看懂谁做了什么、结果怎样。主语可以省，但指代不能含糊。
- 一句话尽量只讲一件主要的事。普通事件优先一两句，重大转折保留必要因果。
- 删除无信息的铺垫、心理描写、总结性评语和重复解释，不删必要的动作、对象、条件或后果。
- 不把名词硬拼成句子，不把普通动作压成四字口号；不用生僻词、半文半白、文艺腔或公文报告腔。
- 不要求每句搞笑、每句有反转、每句以“你”开头，也不限制逗号和句号数量。
- 不按字符数截断，不用省略号掩盖没写清楚的内容。

### 顺口比短更重要

| 不采用 | 问题 | 自然表达方向 |
| --- | --- | --- |
| 轮班表倒让几条险路都有人照。 | 物品代替人行动，搭配含糊。 | 你安排大家轮流巡夜，几条危险的小路都有人照看了。 |
| 鞋印照清了，贼是谁还得动脑。 | 硬接俏皮话，没有讲清线索的局限。 | 鞋印看清了，但还不能凭这个认出窃贼。 |
| 巡夜簿交给巡丁，你留下照路。 | 动作衔接生硬，为短省掉必要成分。 | 你把巡夜记录交给巡丁，接着给大家照路。 |

示范只说明语言标准，不能套写所有事件；是否成立仍以对应分支为准。

## 二、精简冗余，不删因果

按玩家实际阅读顺序分工：

| 位置 | 负责说什么 | 不再重复什么 |
| --- | --- | --- |
| 开局背景 | 年龄、家境和当前处境 | HUD已有的整套身份信息 |
| 事件正文 | 发生了什么，需要处理什么 | 尚未确定的结果 |
| 选项 | 玩家准备做的动作 | 再讲一次完整情境 |
| 选择前说明 | 成本、风险、门槛、耗时和不可逆后果 | 实现术语和无关的内部标记 |
| 检定阶段 | 这次要完成的具体任务 | 整段事件背景 |
| 结果 | 这次实际发生的后果及必要的下一步 | 重讲起因和选项 |
| 成就短评 | 对这段经历的一句评价或补充 | 逐字复述结果或罗列解锁条件 |
| 死因 | 致死原因，克制地结束 | 戏谑受害者、再次讲完整危机 |
| 结算 | 生平与成就汇总 | 在同一屏重复主成就的完整评语 |

事件、阶段、成功、失败、大成功、普通结果、事业中断和完成文本必须分别阅读。不能只改一条通用描述，也不能清空字段掩盖渲染重复；明确的重复输出应在显示层修复。

### 长度仅作软目标

| 类型 | 软目标 |
| --- | --- |
| 普通事件 | 尽量15—35字，通常一两句 |
| 重大情境或结果 | 尽量25—50字，必要时可以超过 |
| 选项 | 通常4—10字，以动作明确为准 |
| 成就短评 | 通常一句自然的短话 |
| 卡牌、事业说明、系统提示和死因 | 以信息完整、准确、容易扫读为准，不设硬字数 |

不要求事件按固定比例分配字数，不规定“严格单行”或“绝不出现第三行”。不能为达标省成病句，也不能缩小字号、隐藏成本、裁掉正文。

## 三、趣味来自遭遇，不来自硬插吐槽

- 保留具体遭遇、人物反应、得失和自然反差；捡漏、误会、出糗和小聪明必须原本就存在于事件中。
- 可以轻松，也允许平实、紧张或遗憾。各事件不必保持同一种段子节奏。
- 不批量套“结果……倒是……”“没想到……竟然……”“你以为……其实……”。
- 不滥用“喜提、直接、当场、竟然、绷不住、赢麻了”等固定词。
- 不为每条结尾添俏皮话、人生感悟或道理；不要靠钱袋、板凳、账本“点头、上班、认路”代替真正的结果。
- 对死亡、灾难及历史人物保持分寸，不拿受害者遭遇制造笑点。

## 四、玩法事实不可变

纯文案修订只改玩家文字，不改ID和跨文件引用、条件、属性数值、概率、奖励、成本、风险等级、事件触发、检定、阶段图、事业推进和结算逻辑。

- “尚未确定”不能写成“已经失败”，“可能”不能写成“必然”。
- 看清鞋印但不能认人，不等于查案全盘失败；一次失败后还有救援，也不能提前写成死亡。
- 卡牌说明必须符合实际能力、消耗、失效条件，不把检定加成写成必胜、免疫或永久有效。
- 不编造原事件没有的行为、奖品、社会评价、人物反应或历史事实。
- 语义不清时继续查条件、效果和调用处，不能凭感觉补剧情。
- 改名后同步所有玩家可见引用，保持不同物品、事业和成就可区分。
- 同一属性统一叫法：**体魄、家资、才干、人脉、气数**；地区、门第、身份、卡牌和事业优先读取生产配置，不另存一套显示名称。

## 五、界面文案与真实阅读宽度

- 按钮写动作，如“管理事业”“查看最新”“重启人生”，不用“批红呈阅”等装饰性古风词代替操作。
- 系统提示说清发生了什么、接下来能做什么，不把错误码、存档版本、内部Flag直接当玩家提示。
- 不可选原因尽量具体，只解释配置和代码能够证明的限制；无法判明时不猜具体缺项。
- 当前界面仅有内存中的未结束人生，统一提示「本局进度仅临时保留，关闭或刷新后不能继续。」不能写成「已保存，下次继续」。本机保留的已完成人生记录和音量设置要与当前进度区分；其他工具的文件存档也不能写成当前界面的续局能力。
- 检查连续阅读的总负担：情境、选项、检定预览、成本、结果和成就是否在反复讲同一件事。风险与必要规则不能为了去重而消失。
- 现行界面是 TypeScript + minigame-canvas-engine 1.0.29 的 XML / Flex 与 Canvas，面向 Web 和微信小游戏。750 是逻辑宽，不是手机可见宽或截图位图像素。以实际 Canvas 可见宽 `W` 换算：`CSS px = 逻辑单位 × W / 750`；DPR 只改变位图密度。正文目标约 16 CSS px 或以上，非关键短标注不低于 12，重要警告目标 13–14 或以上；完整规则以 UI 主规范为准，不把当前固定内容宽或字号当跨设备保证。
- 用实际字体、内容内边距、容器缩放与安全区检查换行。短屏先减少装饰和间距，再让正文滚动，不能为满足软字数而缩字或裁切。按钮、选项和滑块命中区至少 44 CSS px，相邻约 8 CSS px；逻辑命中下限为 `ceil(44×750/W)`，360 宽为 92，390 宽为 85。
- 后续获授权修改文案或显示实现时，在实际 Canvas 下检查手机尺寸的开局、普通事件、重大选择、检定结果、成就、死亡和结算；Web 与微信分别记录。正文应完整换行、可滚动，成本和不可逆后果在选择前可读。独立 HTML 或静态预览证据不等于 Canvas 实现或平台真机验证。

## 六、题材与安全边界

- 不用民族蔑称；军事叙述保持中性，历史人物不恶意丑化。
- 不描写血腥残忍细节，不用“销户、下班、领盒饭”等说法戏谑死亡。
- 奇术、算卦、传言不写成真实灵异或超自然能力；医药不夸大疗效。
- 不宣扬厌世、自残、自杀，不描写赌博操作或其他不良行为细节。
- 轻松表达不是审核保证；自动校验不能替代内容人工审查和平台审核。

## 七、修订与验收

本节约束生产文案与显示修改；本轮全局 UI 实施只读取生产 JSON，不修改生产内容字段。实际构建与运行检查记录于 README，不以规范条目冒充已执行结果。

1. 建立来源及显示位置清单，排除历史归档、第三方、生成副本和不进入玩家界面的调试日志。
2. 按模块逐条读完整事件及全部分支，再改字段；清楚自然的可保留，并记入覆盖范围。
3. 每条读一遍：顺不顺、谁做了什么、因果是否完整、有没有重复或硬梗、有没有改变事实。
4. 检查跨文件名称与属性叫法，确认关键成本、门槛和不可逆风险在选择前可见。
5. 对比修改前后的非文案字段，确保玩法数据和引用不变。文案变化会改变内容指纹，按现有内容装载与指纹机制处理；不篡改旧记录绕过匹配。
6. 生产内容字段变动必须遵守 `AGENTS.md`，完成内容格式／依赖校验与完整测试。当前根 `package.json` 提供 `typecheck`、`build`、`build:wechat` 等命令，没有 `validate:content` 或 `test` 脚本；需先具备实际可用的内容校验和行为／分支测试入口，缺少时如实报告条件不足。不得套用不存在的旧工程命令、声称未执行的检查已通过，或以类型检查／构建成功替代内容正确性。
7. 改显示代码时，在获授权的实施验收中实际打开 Web／微信目标界面，记录操作路径、完整文字、关键条件和可用状态；没有设备证据就不宣称通过平台验收。

只固定旧措辞的测试按项目测试规范处理；保留并运行有效的行为、分支和信息保留测试，不通过删断言或藏内容换绿灯。
