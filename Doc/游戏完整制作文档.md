# 《时空词条：历史重开模拟器》完整制作文档

版本：v1.0

本文件是产品制作依据，按“个人使用 AI 完成游戏”的方式组织。仓库已有本地可配置核心、内容模板及部分测试；命令行和人生流程按下述本地交付范围接入，实际可用性与检查结果以执行记录为准。平台游戏、完整内容与发行仍是后续目标，不能将本地核心当作可运行的完整平台游戏或已通过审核的产品。

## 一、如何使用本文

### 1. 每次只推进一个可验证步骤

每一步都包含：**前置条件 → 制作操作 → 产出 → 完成条件 → 未通过时**。

- 不以“代码已生成”“页面能打开”“AI 说完成了”作为通过依据。
- 规则逻辑需要实际调用引擎；界面需要实际操作；小游戏能力需要在对应平台真机验证。
- 保存本步的命令结果、操作路径、截图或录屏和可回放种子。没有执行的检查标记“未执行”，不要写成通过。
- 账号、签名、资质、平台权限等外部条件无法由代码替代。缺少时记录具体缺项，继续不依赖该条件的工作，不伪造成功。
- 改变规则时先修改本文件，再同步代码、内容和验证用例。不要保留两套互相冲突的规则。

### 2. 每步可直接交给 AI 的执行指令

```text
依据《Doc/游戏完整制作文档.md》，执行第 N 步。
先检查该步前置条件和已有文件，复用现有实现，不重复建立第二套系统。
只实现当前步骤及其必需依赖，不擅自增加功能或改变玩法。
必须处理本步列出的失败情况，不能用假成功、空函数或占位按钮冒充完成。
完成后运行本步可执行的检查；涉及界面必须实际操作，涉及平台能力必须区分预览、模拟和真机证据。
回复：改了什么、实际验证了什么、每条完成条件是否满足、尚缺的具体外部条件。
涉及内容时遵守本文内容安全附录；AI 生成结果只能是待确认草稿，不得自行标记已批准或保证过审。
仅围绕当前步骤的操作、产物、完成条件和实际验证交付。
```

### 3. 制作记录

工程建立后使用 `Doc/制作记录.md` 记录步骤号、状态、产物路径、实际验证、失败项和下一动作。状态只有“未开始 / 制作中 / 条件不足 / 已验证”。内容确认记录放在专用台账，不能用一条聊天里的“看起来没问题”替代。

### 4. 可配置核心：本地与 HTTPS 内容包、抽卡和模拟

本节描述核心和 Node 命令行用法；脚本声明不等于当前环境或未来修改后依然通过。已有本地验证证据见第五节，重新执行时应保留实际结果，执行失败不可记作通过。示例内容仅供开发测试，不代表内容已获批准。HTTPS 内容读取已接入 CLI，不表示已接入微信或抖音小游戏网络与存储。

**环境与命令。** 在仓库根目录使用 Node.js 22.22.1 或更高版本和 npm，先执行 `npm ci` 安装锁文件中的依赖。以下使用不同的状态和输出路径；模拟的 `--out` 必填且目录必须不存在，不会覆盖已有报告。输出、回放和状态目录不能放在内容包内，路径检查也会解析父目录中的符号链接。

```bash
npm ci
npm run generate:content-types
npm run typecheck:core
npm run validate:content -- --content assets/resources/data/ming_end
npm run draw -- --pool POOL_PITY --count 10 --seed 1640 --command-id example-10 --state .local-state/example-gacha --json
npm run draw -- --pool POOL_PITY --count 1 --command-id example-11 --state .local-state/example-gacha --json
npm run play -- --seed 1640 --state .local-state/example-life --export-replay .local-state/example-life-replay.json
npm run replay -- --file .local-state/example-life-replay.json --json
npm run play -- --auto --seed 1640 --state .local-state/example-auto-life --export-replay .local-state/example-auto-replay.json
npm run simulate -- --mode draw --pool POOL_PITY --draws-per-run 100 --runs 100 --seed 1640 --out .local-state/example-draw-report
npm run simulate -- --mode life --runs 10000 --seed 1640 --strategy normal --out .local-state/example-life-report
npm run replay -- --file .local-state/example-life-report/traces/0.json --json
```

`draw` 必须提供 `--pool`、正整数 `--count` 和 `--command-id`；默认状态目录为 `.local-state/gacha`。`play` 默认状态目录为 `.local-state/life`；`--export-replay` 是退出时可选的导出路径，文件已存在时拒绝覆盖。所有内容入口均可指定 `--content DIR` 或 `--content https://HOST/PACK/`，缺省使用 `assets/resources/data/ming_end`。新状态未指定种子时使用 1640；恢复已有状态时省略种子沿用存档种子，显式指定不同种子会报 `SEED_MISMATCH`。种子为 0–4294967295 的整数；批量模拟各局使用 `seed + 样本序号`，超出范围会拒绝。`validate:content`、`draw`、`simulate` 和 `replay` 支持 `--json`：成功 JSON 写入 stdout，错误写入 stderr；`play` 是交互式人类可读入口。参数错误退出码 2，内容、运行或存档错误退出码 1。

**内容制作与 HTTPS 发布操作。** 下面发布的是完整内容包，不是小游戏平台正式上线。按顺序执行；任一步失败、内容又有修改或人工审查未通过，都先停下，修正后重新执行受影响的校验、测试和试玩，不把旧结果当作新版本的证据。

1. **准备和编辑。** 在 Windows PowerShell 中进入仓库根目录；若仓库放在别处，将路径改为实际位置。按上面的环境要求安装依赖；本仓库没有 `npm test` 脚本，全量测试使用 `npx vitest run`。

   ```powershell
   Set-Location 'C:\Users\admin\Documents\pppp'
   npm ci
   ```

   在本地编辑完整的 `assets/resources/data/ming_end/`，不要只准备修改过的文件：包中包含 `manifest.json` 及 `rules.json`、`era.json`、`regions.json`、`castes.json`、`traits.json`、`cards.json`、`pools.json`、`events.json`、`chains.json`、`achievements.json`、`deaths.json` 共 11 个内容 JSON。也可复制整个目录到别处制作，后续命令的 `--content` 相应改为该完整包目录。参照模板、`assets/resources/data/content.schema.json` 和 [文案设计与风格规范](./文案设计与风格规范.md) 修改；保护既有 ID 和跨文件引用，不要随意改名或删除，确需调整时同步所有引用。仅编辑内容包不需要修改源码；新增机制或修改 Schema 则需同步引擎、契约和类型，不能靠增加任意字段实现。

2. **校验、全量测试和新档试玩。** 在仓库根目录执行，检查退出结果；校验失败按文件及 JSON Pointer 修正。校验检查结构与跨文件语义，包括未知字段、重复 ID、悬空引用、权重、阶段图和开局可行性，不会只加载包中合法的一部分。

   ```powershell
   npm run validate:content -- --content assets/resources/data/ming_end
   npx vitest run
   $LocalState = ".local-state/release-local-$([guid]::NewGuid())"
   npm run play -- --content assets/resources/data/ming_end --seed 1640 --state $LocalState
   ```

   试玩使用全新独立状态目录，手动体验开局、选项、阶段和结局；菜单操作见下方“试玩、存档与回放”。也可另用新目录加 `--auto` 跑一局，但自动试玩不能代替人工体验。记录命令、结果和问题；任何修改后重新校验、全量测试并用新档试玩。

3. **人工审查与冻结版本。** 上线前逐项阅读本次内容，检查文案风格、敏感内容、历史人物与题材、分支表现和实际玩法，按文案规范及当时适用的平台要求由人员确认并记录；自动校验和测试不等于内容审批。审查不过或要求无法确认时停止发布。确定发布版本后，在 `manifest.json` 更新 `content_version`，保留正确的 `content_id` 和 `files` 相对路径；版本号应与已发布版本区分。版本变更也是内容变更：再次执行第 2 步的校验、全量测试和新档试玩，记录最终本地校验输出中的内容 ID、版本和指纹，并确保最终包与人工审查记录一致；之后若再改内容，重新审查并重复这些步骤。

4. **上传完整包并核验。** 将最终 `manifest.json` 和它引用的全部 11 个 JSON 按原有相对目录结构上传到新的、不可变的 HTTPS 版本目录，不覆盖已发布目录，不只上传差量。`manifest.files` 只能填写包内相对路径，不能写独立 URL 或越出包目录；可信 Schema 始终来自本工程的 `assets/resources/data/content.schema.json`。通过实际使用的托管服务完成上传，并确认全部文件可从该目录访问后，才将该地址用于校验或提供给使用方；不要在上传中途切换使用地址。上传方式、权限和目录地址以实际服务配置为准。

   在 PowerShell 输入实际 HTTPS **目录地址**（不是 `manifest.json`；末尾 `/` 可省略），然后校验远程完整包并对照第 3 步记录：

   ```powershell
   $ContentUrl = Read-Host '输入已上传完成的 HTTPS 内容包目录地址'
   npm run validate:content -- --content $ContentUrl --json
   ```

   确认输出 `ok` 为 `true`，`content_id`、`content_version` 和 `fingerprint` 与最终本地校验一致；失败或不一致时停止使用该地址，查明并修复后重新核验，不关闭证书验证。再用另一个新状态目录从远程包试玩，确认输出指纹一致且开局、推进和结局正常，例如：

   ```powershell
   $RemoteState = ".local-state/release-remote-$([guid]::NewGuid())"
   npm run play -- --content $ContentUrl --auto --seed 1640 --state $RemoteState
   ```

   记录实际远程目录、版本、指纹、校验及试玩结果，再向使用方提供该地址。远程试玩仅验证 CLI 加载和本地运行，不代替平台真机、审核或发行验证。

内容指纹按规范化后的完整包计算；文案、数值、数组顺序或版本等变更可改变指纹，单纯 JSON 空白或对象键顺序变化不改变指纹。存档和回放严格匹配内容标识、版本与指纹：指纹变化后旧档不能继续，不能篡改存档或指纹强行绕过；保留原始存档和对应旧包。回退到旧包也受此限制，已在新包创建的存档不能直接用于旧包，当前没有存档迁移能力。

HTTPS 入口拒绝 HTTP、URL 内嵌凭据、查询串和片段；文件路径拒绝父目录、绝对路径、反斜线、百分号编码、空白、查询串、片段以及空或 `.` 路径段，嵌套目录可用。请求禁止重定向，即使重定向仍在同源也会失败，防止跳出原始 origin 和包路径。使用系统信任链验证 TLS，不允许通过关闭证书校验绕过错误。每个请求（含响应体读取）超时 15 秒；顺序读取全部文件，不自动重试，当前没有响应体大小上限或全包总时限。HTTP 失败、网络失败、非法 JSON、Schema 或跨文件语义错误均拒绝加载，不发布部分 bundle。

本地和远程使用相同的完整包组装、校验、规范化 SHA-256 指纹和深冻结逻辑，运输方式不进入指纹。当前没有服务端版本锁定或签名协议，不保证正在原地覆盖的多个文件来自同一部署批次。CLI 的状态、回放和模拟报告仍是本地文件；本地内容包的防覆盖与符号链接检查保持不变。

`assets/scripts/application/ContentPackage.ts` 提供平台无关的读取、组装与完整校验流程，宿主注入文本读取、可信 Schema 校验及指纹函数；核心没有引入 Node。`tools/lib/ContentLoader.ts` 是实际的 Node 文件系统 / HTTPS 适配，不是小游戏适配器。目前没有微信 / 抖音小游戏 SDK 适配、网络域名配置、下载缓存、持久存储适配或真机验证，也没有离线缓存、缓存回退、SafeMode 或首包自动裁剪。断网或校验失败会报错退出，不能宣称可离线启动、自动进入安全内容模式或已完成首包优化；未来小游戏宿主还必须接入真实 SDK 并验证这些能力。

**真实本地 HTTPS smoke。** 在仓库根目录运行下面命令；临时证书不进入仓库，服务只托管预先读取的 manifest 和 11 个文件，不暴露任意磁盘路径：

```bash
CERT_DIR=$(mktemp -d)
export CERT_DIR
openssl req -x509 -newkey rsa:2048 -nodes -keyout "$CERT_DIR/key.pem" -out "$CERT_DIR/cert.pem" -days 1 -subj /CN=localhost -addext 'subjectAltName=DNS:localhost,IP:127.0.0.1'
node --input-type=module <<'JS' &
import { createServer } from 'node:https';
import { readFile } from 'node:fs/promises';
const root = 'assets/resources/data/ming_end/';
const manifest = JSON.parse(await readFile(root + 'manifest.json', 'utf8'));
const files = new Map(await Promise.all(['manifest.json', ...Object.values(manifest.files)].map(async file => ['/' + file, await readFile(root + file)])));
createServer({ key: await readFile(process.env.CERT_DIR + '/key.pem'), cert: await readFile(process.env.CERT_DIR + '/cert.pem') }, (req, res) => {
  const body = files.get(req.url);
  res.writeHead(body ? 200 : 404, { 'content-type': 'application/json' });
  res.end(body ?? '{"error":"not found"}');
}).listen(8443, '127.0.0.1', () => console.log('HTTPS smoke ready: 8443'));
JS
SERVER_PID=$!
# 看到 HTTPS smoke ready 后执行；随后可用相同环境变量运行 draw/play/simulate/replay。
NODE_EXTRA_CA_CERTS="$CERT_DIR/cert.pem" npm run validate:content -- --content https://127.0.0.1:8443/ --json
# 全部 smoke 完成后：
kill "$SERVER_PID"
rm -rf "$CERT_DIR"
```

服务端使用该 `key.pem` / `cert.pem`；客户端以 `NODE_EXTRA_CA_CERTS` 增补信任，禁止设置 `NODE_TLS_REJECT_UNAUTHORIZED=0`。也可为上面的 draw / play / simulate / replay 命令加上该 HTTPS 目录作为 `--content`，并对照本地包指纹；可用远程包生成回放再用同一本地包回放。测试还应覆盖 404、302、非法 JSON、路径逃逸和超时，退出服务并删除临时证书与输出。

内容作者可替换文案、词条、卡牌、事件、链、成就、条件、效果及既有机制的概率与数值；条件和效果是 Schema 规定的受限操作，不执行脚本或插件。五属性、D20 自然 1/20、年度处理顺序和现有条件 / 效果操作符属于固定机制；新增属性或机制需要升级契约和引擎，不是填入任意字段即可生效。`events.json` 的 `trigger_probability` 是候选门控概率，之后仍按候选的 `weight` 竞争，并非最终命中率；`luck` 只调整标记为稀有的随机事件权重。选项和阶段结果按配置效果执行；手动试玩每个阶段需要明确确认，全自动试玩和批量模拟则逐次提交阶段确认，不跳过检定。

**独立卡池。** `cards.json` 定义卡牌及展示用稀有度；`pools.json` 的 `entries` 为卡牌 ID 和非负权重，普通抽取的基础概率为权重除以候选权重总和，零权重不会抽中。稀有度只是标签，没有额外的暗中稀有度抽样。`hard_pity.after` 表示连续未中目标后最迟第 N 抽限定在 `target_card_ids` 目标集合中，提前自然命中也会重置计数；保底抽显示的是当抽候选集合中的条件概率，不是长期综合概率。`POOL_PITY` 样例是第 10 抽硬保底 `CARD_EPIC`；`POOL_BASIC` 无保底。`replacement: false` 只在一次 `draw` 调用内不重复，下一次调用重新提供全部候选，单次数量不得超过正权重卡数；无放回不能与硬保底组合。独立卡池不进入人生词条、库存或货币系统。

同一状态目录中，各卡池的随机状态和保底计数独立保存。重试相同 `command-id` 和相同参数会返回原结果，不再抽卡；同一 ID 换参数会报冲突。要继续抽取，使用新的命令 ID；十连是逐抽处理，已存保底不会因 CLI 重启清零。

**试玩、存档与回放。** 默认手动 `play` 菜单支持 `status` 查看、`next` 推进一年、`auto` 逐年推进至决策或重要变化、`choose <optionId>` 选择、`stage` 确认当前阶段、`retire` 在已达成可谢幕成就时结束、`save` 和 `quit`。遇到待选项或阶段时先处理该输入；手动模式 EOF 等同退出，不会代选。已结束的存档保留结局；想免费重开请使用新的 `--state` 目录。

启动参数 `play --auto` 是全自动模式，与菜单中的 `auto` 不同：不等待终端输入，从当前可用选项中等概率随机选择，自动确认每个骰子阶段并逐年推进，直至死亡等自然结局，不自动谢幕。每条命令保存成功后才继续；错误时停止，Ctrl+C 等当前命令保存后退出。同一 `--state` 下重启并加 `--auto` 即可继续已有进度。随机选择使用内容指纹、人生种子和事件实例派生的独立随机源，不消耗事件/骰子的游戏随机流，也不改变存档格式；同内容、同种子、同路径可复现，恢复同一待选事件不会重新随机。想体验不同人生，请使用新种子和新状态目录。所有自动选择与阶段确认都记录在原有回放中。

终端试玩的剧情正文以青色显示，年月、年龄和属性状态保持默认颜色，方便区分剧情与数值。输出到管道或文件时自动使用纯文本；也可用 `NO_COLOR=1 npm run play -- --auto` 关闭颜色。抽中事件的候选审计日志仍保存在存档中，但不作为剧情重复打印，剧情以事件实际开始执行时的记录为准；无事件时的平年提示和独立的结果文案仍显示。相同文字若来自不同事件、不同年份或不同结果，不按文字去重。

状态目录采用 `state.lock` 独占锁和 `slot-a.json` / `slot-b.json` 双槽保存；第二个使用同一目录的进程会被拒绝。异常退出留下锁时，先确认原进程已经退出，再按提示处理锁文件，不能抢占仍在使用的状态。每槽保存独立递增的存储 revision、内容和 SHA-256 校验和；它与引擎 revision 不同，内容未变化不重写。写入先同步临时文件，再重命名并同步目录；恢复选择校验有效且 revision 最高的槽。只有两个槽均不存在才视为新档；已有文件但全无效时报 `SAVE_CORRUPT`，同 revision 内容冲突时报 `STATE_CONFLICT`，均保留文件。写入结果不确定时重新读取确认，无法确认则停止，不凭旧内存重复抽取或推进。存档绑定内容 ID、版本和内容指纹；即使版本号没变，只要内容变更导致指纹不同，旧档也会拒绝加载，不会静默迁移、清空或回退到另一内容的旧槽。保留旧包与旧档，换新状态目录使用修改后的包。

回放记录种子及实际命令，逐命令比对结果；正常回放还核对仅由引擎 `exportSave()` 计算的最终状态哈希。一个例外是人生初始化尚未提交时，自动结果无法应用（例如任务容量不足）：这时没有可导出的 `GameSave`，批量模拟失败记录的 `save` 为 `null`，回放只含失败的 `initGame` 命令且 `expected_final_hash` 为 `null`；回放核对并重现该错误，不虚构存档或终态哈希。`replay --content DIR --file FILE` 必须使用相同内容，偏离会报告首个不同的命令。模拟不读写玩家存档：`--mode life` 默认使用人生模拟，`--mode draw` 必须另给 `--pool` 和正整数 `--draws-per-run`。`--strategy normal` 选择内容顺序中的首个可用选项，`cautious` 优先 safe、normal、high，`risky` 优先 high、normal、safe；同等级保持内容顺序，阶段仍逐次确认，默认不主动谢幕。

模拟输出 `summary.json`、逐局 `runs.jsonl` 和每局 `traces/<index>.json`；失败样本保留错误、可用的状态及回放（初始化未提交时状态为 `null`），计入失败数并使进程退出非零。人生报告按年龄段与开局死、长寿 / 重大、短局、常规路线分层，列样本数、年龄 / 年数 / 阻塞输入的 P50/P90、前三年死亡率及任务和结局频数；无任务启动时完成率为 null。阻塞输入按开局确认、成功选项和成功阶段确认计数，`estimated_input_seconds` 仅为输入数乘 5 秒，不是实测时长，也不能证明两分钟目标达标。抽卡报告区分基础权重概率与含保底的实际频率，并记录保底触发和未命中段。

## 二、固定的产品与玩法规则

### 1. 游戏目标

带着现代词条，随机进入历史中的不同年龄、地区和门第，在时代条件下做短而明确的选择。结果可以是开局即结束、平凡一生、完成长期事业或产生架空历史影响。

首发为真正的**微信小游戏和抖音小游戏**；之后分别制作 TapTap Android 和 iOS。核心保持纯 TypeScript，表现使用 Cocos Creator + TypeScript，平台能力通过 `PlatformBridge` 接入。不把普通小程序包当小游戏，不额外套 Capacitor，不要求重写 C++ 游戏逻辑。

首发不做多人、交易、排行榜、自由输入昵称、UGC、在线 AI 生成剧情、跨设备云存档或复杂内容后台。没有实现的功能不出现入口。首发采用免费完整玩法加可选激励广告；原生数字商品只有在明确启用并完整实现后才出现。

### 2. 快节奏与真实游玩时长

**以玩家约 5 秒完成一次选择为测量基准，正常一局约 2 分钟，常见范围 30 秒至 5 分钟。** 长寿或重大结局通常 3–5 分钟；允许开局直接死亡，几秒内结束。5 秒不是倒计时，慢读、暂停或无障碍操作不触发自动选择或强制死亡。

| 人生路线 | 阻塞输入参考 | 目标表现 |
| --- | --- | --- |
| 天崩开局 | 0–2 次 | 约 3–15 秒，简述原因后结局，一键免费重开 |
| 短局 | 5–9 次 | 约 30–60 秒，快速形成反差结局 |
| 常规局 | 16–22 次 | 自动展示等开销约 10–15 秒，约 90–125 秒；常规样本中位目标 90–120 秒 |
| 长寿 / 重大结局 | 30–54 次 | 自动展示等开销约 15–30 秒，预算约 165–300 秒，通常 3–5 分钟 |

计时从发起本局开局到完整结局卡可操作。`T_play = 5 秒 × 阻塞输入数 + 实际展示与计算开销`。开局确认、选项、每阶段确认、手动继续及结局卡出现前必需的确认均计入；结局卡后的分享、退出和下一局另计。

冷启动、广告、网络等待、离开应用和主动回看档案另外记录，同时报告真实会话总时长。不得用大量秒死降低总体平均数冒充“两分钟体验”，不得隐藏广告造成的打断。

**压缩展示，不删除因果：**平年与无决策结果自动逐年计算、合并摘要，不要求每年点击。遇到选择、检定、任务交互、重要身份变化、死亡或重大结局必须停在对应节点。不能直接加若干岁后补算，也不能为了满足时长提高死亡率。

### 3. 随机年龄与历史年份

先按年龄段权重抽取，再在段内均匀抽整数；下表是首轮调参值，不是已经验证的平衡结果。

| 年龄段 | 权重 | 优势 | 成本与适合路线 |
| --- | --- | --- | --- |
| 幼年 3–10 | 25% | 成长窗口长、长期积累机会多 | 身体与行动受限、依赖家庭，可能早夭；适合长期事业 |
| 青年 11–20 | 30% | 成长和行动能力较均衡 | 资本、身份和声望不足；适合学习与身份跃迁 |
| 壮年 21–45 | 30% | 职业能力、资源和关系可立即发挥 | 家庭责任、债务与既有牵连；适合参与关键事件 |
| 年长 46–65 | 15% | 继承阅历、信用、身份和关系 | 健康压力、剩余年度较少；必须有可在 1–2 年产生结果的路线 |

年长流民不能凭空拥有士绅家产；幼年富户不等于能自由支配家庭财富。用简短继承生平说明起点优势与包袱，身份权限由年龄、门第和事件条件共同决定。

明末开局公历为 1640。`age` 和 `calendar_year` 分开保存，每次年度推进各加 1；同年事件、动画、广告和恢复存档不加年。

真实历史题材限定明及以前，这是项目范围，不是对所有平台法规的概括。重点历史窗口为 1640–1644；**1644 年历史调度阶段完成后切入架空延续，即使没有命中地区限定事件也要切换**。后续内部年份继续增加，对外从下一年显示“架空延续第 1 年”及年龄，不引入清代或近现代真实政治人物、事件，不把架空延续当史实。

主屏显示“架空推演”标记，可展开“本作含架空历史推演与文学构想，不作为史实依据”。该声明不是审核豁免。跨过历史窗口不强制结束人生，年轻角色仍可成长至寿终。

### 4. 属性、D20 与成长

四项可见属性：`physique` 体质、`intelligence` 智谋、`wealth` 可支配资源等级、`prestige` 声望；隐藏 `luck` 气运。五个字段均为 0–10。财力不是精确货币，首发不再并行维护另一套货币账本；债务和家庭控制用生平标记与事件表达。

初始基值为 3，依次叠加年龄、门第、地区、生平和词条修正，再截断到 0–10：

| 年龄段 | 体质 | 智谋 | 财力 | 声望 |
| --- | --- | --- | --- | --- |
| 幼年 | -2 | 0 | -2 | -2 |
| 青年 | 0 | 0 | -1 | -1 |
| 壮年 | +1 | +1 | +1 | +1 |
| 年长 | -1 | +2 | 0 | +2 |

这些是调参初值；门第与生平必须避免矛盾组合。成长不能每年全属性加一；由学习、工作或事件结果决定，可延续已经选择的行动方向，减少重复点击，但不自动代选新路线。

`判定总值 = 原始 D20 + 对应可见属性 + 词条 / 情境修正`。修正合计限制在 -3 至 +3；初始 DC 使用 10 / 14 / 18 / 22。自然 1 恒失败，自然 20 恒成功，但不自动死亡、加奖或跳过下一阶段。确定性结果不伪装成检定。

例：智谋 4、修正 +2、DC 14，成功率为 65%；两个条件不变且独立的阶段连过概率为 42.25%，不能把单阶段概率冒充整条路线概率。

`luck` 只影响配置明确的稀有事件权重，初始因子范围 0.8–1.2，默认 1；不暗改骰子、DC 或已显示概率。

开局 `max_lifespan` 从 65–85 中满足 `max_lifespan >= age + 3` 的整数抽取并保存。它是玩法参数，不是历史平均寿命。事件或伤病仍可提前致死，包括开局直接死亡；寿命上限不是存活承诺。

### 5. 年度、链与死亡

状态：`READY / ADVANCING / AWAITING_OPTION / AWAITING_STAGE / DEATH_PENDING / ENDED`。

`initGame` 处理 1640 开局，不加年。`nextYear` 仅 READY 可用：年龄与年份 +1 → 寿命 / 伤病 → 到期任务 → 历史节点 → 随机事件 → READY。任何阶段需要选择就保存游标并暂停；死亡立即终止剩余队列。

普通危机有可行路径，专属高危选项明确风险；不固定“60% 必死”。开局直接终局是独立类型，可以没有选项，不伪造求生机会，不插入复活广告。

三年任务统一为 Y 年启动，Y+1、Y+2、Y+3 各推进一次，Y+3 完成。初始同时进行上限 2 条。破产、重伤、流亡等配置条件导致中断：不退已花资源，不发完成奖；切后台和等待选择只是暂停。每次相关状态变化后重新检查中断条件。

复活仅每局一次，只针对具备 `rescue_outcome` 的事件死因；自然寿尽、不可救终局及开局直接终局不复活。恢复致死阶段前的世界快照，应用固定撤退 / 受伤结果，结束致死事件并继续当年队列。不重掷、不保送成功、不领原成功奖；保留致死检定已消费后的随机数游标，权益账本不回滚。

大括号是文件清单缩写，不是实际文件名。Cocos 自动生成的 `.meta` 等必要工程文件必须保留。具体原生 SDK 文件在确认对应版本后添加，不编造不存在的插件。

### 核心边界

下表是完整产品接口目标；本地核心当前范围不提供 `applyRevive`、`acceptDeath` 或权益接入。未来实现前不得将这些接口标记为已完成。

- Core 不导入 `cc`、DOM、`wx`、`tt` 或原生 SDK；可在 Node 中推演。
- `GameSession` 协调命令、持久化、节奏和展示；UI 不直接改权威状态。
- 平台门面显式说明能力是否可用，不能把“不支持”伪装为“成功”。
- 内容和美术使用稳定资源 ID；动画随机数独立于游戏 PRNG。
- 配置用 JSON Schema 作为结构源，生成 `content.generated.ts`；不手工维护两套会漂移的配置类型。

| 接口 | 必须做到 |
| --- | --- |
| `initGame(options)` | 校验剧本、词条、锁定权益和种子，创建开局并处理落地事件 |
| `nextYear(commandId)` | 仅 READY 推进一次，返回状态、日志、待决策和效果 |
| `resolveOption(commandId, eventInstanceId, optionId)` | 校验活动实例、选项条件和重复提交 |
| `resolveStage(commandId, eventInstanceId, stageId)` | 只处理当前阶段一次，保存骰值和结果 |
| `applyRevive(commandId, grantId)` | 仅在合法死亡窗口应用一次已核验权益 |
| `acceptDeath(commandId)` | 关闭救援窗口，进入正式结局 |
| `retire(commandId)` | READY 且已达成可谢幕结局时结束，不伪造死因 |
| `generateEndingReport()` | 只读报告，不重复发点数 |
| `exportSave()` / `restoreSave(data)` | 完整保存与恢复决定性状态 |
| `GameSession.advanceToDecision(commandId)` | 逐次推进无决策年度，到阻塞点停止，保存父 / 子命令游标 |

### 本地人生核心接口

本地 `GameEngine` 使用已加载的内容包及其指纹构造：`new GameEngine(content, fingerprint)`。它与上表的完整产品目标有意区分，不接入锁定权益、救援或复活。核心保持纯 TypeScript，文件和终端操作由外层负责。以下是代码接口约定，不是集成或测试已通过的声明。

- `initGame({ seed })` 只初始化一次，生成开局并处理开局调度；重新开局须构造新实例。`current()` 返回当前展示快照和待决策，尚未初始化时不能读取。
- `nextYear(commandId)` 仅在 `READY` 推进一年；`resolveOption(commandId, eventInstanceId, optionId)` 处理当前选项，`resolveStage(commandId, eventInstanceId, stageId)` 明确确认当前阶段并执行其检定；`retire(commandId)` 仅在 `READY` 且已达成可谢幕成就时结束。
- 命令成功返回 `{ ok: true, state, logs, pending }`，失败返回 `{ ok: false, error: { code, message }, state }`。`pending` 区分选项和阶段，选项包含是否可用及不可用原因；展示快照不暴露命令回执或完整日志。失败的领域命令不提交状态、修订号或随机数变化。命令 ID 相同且参数相同会返回原成功结果，参数不同则报 `COMMAND_ID_CONFLICT`；过期决策或不可用选项不得重复结算。
- `generateEndingReport()` 只在终局后返回报告，未结束时报 `RUN_NOT_ENDED`；报告含死因或谢幕原因、成就、最高身份、任务结果、关键决策和最终属性，不产生局外奖励。当前状态集合是 `READY / ADVANCING / AWAITING_OPTION / AWAITING_STAGE / ENDED`，没有后文产品目标中的 `DEATH_PENDING` 救援窗口。
- `exportSave()` 导出含内容标识、指纹、修订号及玩家、运行状态和日志的 `GameSave`。`restoreSave(data)` 校验包和存档：从保存的种子与按修订号排序的成功命令回执重建，再与完整存档比较；错包报 `CONTENT_MISMATCH`，无法匹配的状态或未知字段报 `SAVE_INVALID`，拒绝时保留原引擎状态。这是核心恢复，不替代外层双槽文件保存和会话游标。

### 第 03 步：定义数据契约与内容校验

**前置条件：**核心目录与运行环境可用。

**制作操作：**
1. 在 `content.schema.json` 定义剧本、地区、门第、词条、事件、阶段、链、死因、成就、资源与氛围。

### 第 04 步：先建立内容安全扫描与批准门禁

**前置条件：**Schema 能识别所有可见文本字段；阅读本文内容安全附录。

**制作操作：**
1. 建立 `content-policy/rules.json`，将规则分为 BLOCK / REVIEW / INFO，区分词语命中和情节含义，不简单全局替换。
2. 实现结构化扫描，覆盖正文、选项、阶段、成就、死因、词条、UI、海报、分享、字幕和商店材料；展开模板组合，保留原文位置。
3. 建立 `review-ledger.json`，记录具体内容版本、哈希、规则版本、阅读确认结论、理由、有效范围和时间。AI 不能自行批准自己的输出。

**产出：**规则、扫描报告、确认台账、最小批准清单生成、构建门禁和运行时加载门禁。

**完成条件：**BLOCK 阻断；未确认 REVIEW 阻断；改一个可见字或资源后旧批准失效；未经批准的新包不展示；无安全兼容包时保留存档并显示已审错误提示；误报例外只能针对具体规则与内容哈希。

**未通过时：**不能开始批量扩写或发布内容。开发用负例只在测试范围，不能打进玩家可见产物。

### 第 05 步：制作第一组可验证内容

**完成条件：**实际跑出普通生路、条件锁定、阶段一失败、阶段一成功后阶段二失败 / 成功；自然 1/20 优先级正确，确定性结果不掷骰，重复操作不变更状态。

### 第 08 步：实现逐年状态机和历史节点

**前置条件：**选项与阶段能暂停、继续和终止。

**制作操作：**

4. 历史节点按公历与地区 / 前提触发，任务标记可改变后续节点分支。
5. 完成 1644 历史调度后一次性进入架空状态，没有符合条件的节点也切换。

**产出：**`GameEngine` 年度状态机、`EventScheduler` 和历史分界状态。

**完成条件：**待选择时不能再过一年；同年多个事件按固定顺序执行；死亡立即停队列；不同起龄在同公历触发符合条件的节点；重启不重复历史事件或架空切换。

**未通过时：**修状态机和数据，不新增剧情特例绕过统一计时。

4. 中断记录原因和既有消耗，完成奖励使用唯一提交标识；超出同时进行上限时在开工前提示。

**产出：**可跨年恢复的任务实例、任务日志、完成 / 中断结果。

**完成条件：**1640 年 9 岁启动，在 1641/10、1642/11、1643/12 推进并完成；中途重伤 / 迁移可中断；切后台不算中断；重复恢复不再次发奖。

**未通过时：**修节点游标与幂等，不以缩短年数或丢弃队列解决。

### 第 10 步：实现关键节点交互与自动逐年推进

**前置条件：**年度与链可以单步正确执行。

**制作操作：**
1. 在 `GameSession` 实现 `advanceToDecision`，保存父命令、子命令序号和暂停原因。
2. 一次授权后自动推进无决策年度，平年和自动任务进度合并年段摘要，可展开完整记录。
3. 遇选择、D20、任务交互、重要身份展示、死亡、重大结局停止；阶段确认不省略。纯展示后只在原授权有效且无新决策时续行。
4. 每帧最多处理 4 年或累计约 4ms 后让出；不可分割的单步超过软预算时记录并优化，不拆坏状态提交。后台、保存失败、门禁拒绝立即暂停。
5. 常规路线初值为整局 8–12 个可选随机交互事件，为多阶段与链保留输入空间；不压掉已承诺事件。

**产出：**自动推进控制、摘要日志、输入计数和节奏数据。

**完成条件：**不用点击几十次“下一年”；自动模式与同种子同决策手动单年模式最终状态、骰序、链进度和奖励一致；慢读不会被自动代选；任何死亡都不会被自动跳过。

**未通过时：**调整重复确认、展示和可选内容频率，不通过隐藏危机、跳年或强制早死压时间。

### 第 11 步：实现可靠存档、恢复和版本迁移

**前置条件：**核心和会话的决定性状态已明确。

**制作操作：**
1. `SaveCodec` 显式转换 Set / 数组，保存内容与结构版本、PRNG、队列、阶段结果、命令去重、任务与权益账本。
2. 使用双槽快照、revision 和完整性校验，恢复最高有效版本，不假设多个存储 key 是事务。
3. 在开局、队列固化、选择 / 阶段提交、任务结果、年度完成、死亡 / 复活 / 结算处保存；可靠保存后才继续自动推进。
4. 固定每局内容版本。只支持明确实现的迁移；损坏或不兼容时保留原档并提示。
5. 后台仅保存和暂停，不按真实离线时间推年。

**产出：**`SaveCodec`、迁移逻辑、平台存储端口和错误提示。

**完成条件：**两阶段中途退出再进仍是相同骰值与阶段；一槽损坏能用另一槽恢复；两槽无效不假装新进度；保存失败不显示“已保存”；同命令恢复后不重复生效。

### C. 扫描、逐条审阅与批准

**前置条件：** 内容、模板、规则版本及资源清单已固定，准备内部审核记录；AI 草稿尚未批准。

**制作操作：** 对事件、选项、阶段、死因、成就、词条、默认昵称、UI、海报、分享标题、字幕和商店材料进行结构化扫描，覆盖本地包及候选 CDN 内容；识别 JSON 字段与引用，展开模板代表性组合。识别时规范化 Unicode、零宽字符和空白，报告保留原始位置。报告记录文件、JSONPath、规则 ID、上下文和严重度；敏感上下文仅留内部，不打包、不对外埋点。逐条阅读并记录结论，检查真实可达的完整路径、条件、后果与奖励，另逐项检查图片、音频和视频。AI 不得代替此项确认。

BLOCK 命中即阻断，整改或删除后重扫；REVIEW 逐条阅读并记录结论，不能判断则不放行；INFO 供关注，不是安全证明。扫描未命中也不能跳过逐条审阅。真实风险不是误报；经核实的误报例外仅绑定具体内容 hash 与规则 ID，记录确认操作、理由、批准版本和到期时间，不设通配白名单。内容或资源改变、规则或政策版本变化、批准到期时，受影响批准及例外失效，重新扫描、审阅并记录。

**产出：** 规则版本、扫描报告、逐条审阅结论、路径及视听检查记录、必要的具体误报例外。

**完成条件：** BLOCK 已消除，REVIEW 均有明确结论，完整路径及视听素材已逐项检查；不能仅凭名称、无命中或 AI 自评放行。

**未通过时：** 退回修改或删除，重新扫描并逐条阅读受影响内容；争议或证据不足时保持阻断，不发布。

### D. 版本证据与运行时门禁

**前置条件：** 候选本地及 CDN 内容均已完成上述审核，确定内容版本、资源及规则版本。

**制作操作：** 内部台账绑定 `content_version`、全部文本与资源 hash、`policy_version`、批准版本、结论、时间和确认操作，并保存扫描、人工路径与视听记录、例外、构建标识和平台复核证据。详细台账及敏感上下文不进入玩家包。另从有效台账生成受信的最小批准清单，包含核验所需的内容版本、完整性 hash、政策与批准版本及有效期；清单须有可验证来源与防篡改机制，不能信任内容包自报 `approved`。

运行时展示前以受信清单核验包版本、全部内容及资源完整性和批准有效性；CDN 包同样先审核、固定版本再校验。新包缺批准、过期、被篡改或不兼容时拒绝加载，改用兼容且批准仍有效的本地版本；无可用包则显示预先审核的错误提示、保留存档并停止游戏。不得先展示再替换、临时洗稿或用占位文案改变剧情。回退也须重新核验有效批准。

**产出：** 内部版本台账、受信最小批准清单和发布候选包。

**完成条件：** 台账、清单与实际包的版本和 hash 一致，所有批准有效；缺批准、变更、过期、hash 不符、无可用回退等负例均按上述门禁阻断或保档停止。

**未通过时：** 停止导出、发布或加载；修复并重新审核受影响内容，生成新的受信清单，不沿用旧批准。

### E. 官方证据与渠道准入

**前置条件：** 已确定目标渠道、实际玩法、展示内容及账号；提交前重新查看官方现行政策并保存链接、查阅日期与答复。

**制作操作：** 核实 [微信通用文本检测 msgSecCheck](https://developers.weixin.qq.com/miniprogram/dev/server/API/sec-center/sec-check/api_msgseccheck.html)及[微信小游戏专用文本检测 gameMsgSecCheck](https://developers.weixin.qq.com/minigame/dev/api-backend/wxa-sec-check/api_gamemsgseccheck.html)的账号权限、场景与静态剧情适用要求。通用文档列有小游戏适用范围，游戏专用接口仍可能需要账号配置，不能因此假定已经开通。首发无自由输入昵称、UGC 或在线 AI；生产和加载门禁不代表平台豁免静态剧情检测。若将来增加动态输入，先分别核实各平台要求；待检测内容不公开、不进分享，拒绝、超时或服务不可用均停止公开，服务端凭据留在服务端。

复核[抖音小游戏自审标准](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/operation1/norms/standards)：其提示暂不接入低质文字类、疫情相关游戏及无版号宫斗官斗；本项目文字互动、涉及防疫的内容和身份路线是否适用，必须向平台结合实际玩法确认，不能推断所有文字游戏均被禁止，也不能用防疫别名绕审。玩家文字输入的检测要求及小游戏可用接口应分别核实，不套用微信接口。按[抖音适龄提示](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/operation1/norms/right-age)和实际内容申报，不预设统一年龄等级。

**产出：** 各渠道政策、接口、账号资格及题材适用性的留证与确认结论。

**完成条件：** 当前官方要求与实际账号条件已核实，所有不确定项有明确平台答复或已移除对应内容并重新审核；检测结果仅是判断信号，不是发行许可。

**未通过时：** 停止对应渠道提交，补充官方确认或调整内容后重新核查；不保证过审，不将其他渠道结果视为该渠道许可。
