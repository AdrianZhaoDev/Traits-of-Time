# 04｜图鉴、重开与逻辑修补

> **状态：分批实施中。**本文保留提出方案时的旧版核查、拟议条件和验收要求，不把当时的配置快照当作现状；当前实现、逐 ID 证据和已执行检查分别见 [README](../../README.md) 与 [逐 ID 目录核查](图鉴逐ID核查.md)。跨界面方案见 [03](03-界面阅读与交互减法.md)，玩法变化见 [01](01-玩法数值与人生节奏.md)，具体文案遵守 [文案规范](../文案设计与风格规范.md)。

## 一、方案提出时的事实与未核实范围

1. [开局池](../../assets/resources/data/ming_end/pools.json) 的 `POOL_NATIVE_LIFE` 只有六张正权重现代卡；[EffectExecutor.ts](../../src/game/core/engine/EffectExecutor.ts) 的效果分支没有添加卡牌。原生书、碗仍在卡表，至少 20 个成就条件直接要求持有 `CARD_NATIVE_BOOK` 或 `CARD_NATIVE_BOWL`，例如 `A_NATIVE_BOWL_CONGEE`、`A_NATIVE_BOOK_PETITION`。因此这批成就在**现行正常新局路径**不可达；这不是说所有非原生条目均已证明可达。
2. [CollectionProgress.ts](../../src/game/presentation/CollectionProgress.ts) 以当前 `bundle.achievements` 和 `bundle.deaths` 的整个数组计总数，只计记录中同 ID 的已收集；未知历史 ID 保存在记录集合，但当前图鉴遍历内容包不保证能显示。当前并没有可达目录过滤。
3. [LifetimeRecords.ts](../../src/game/presentation/LifetimeRecords.ts) 按人生 ID 去重，保留成就 ID 与死因 ID；传承用 `inheritanceRewardId` 和含 `rewardId/lifeId/state` 的 claim 做预留与核对，并非每个 claim 保存已选奖励。旧记录可能没有死因。[schema.ts](../../src/game/core/types/schema.ts) 的 `InheritanceBonus` 仍包括单属性和 `extra_card`，后者也可能存在于真实人生存档的 `run.inheritance`、初始化重放命令中。
4. [家庭交付记录](../家庭内容交付.md) 已明确：旧成长/孙辈事件部分只查玩家年龄和 `F_LIFE_HAS_CHILD`，缺出生时间或存活约束；`F_FAM_CHILD_1/2/3` 是出生里程碑而不是存活数。哪些具体事件仍有问题，须逐事件追条件和效果，不能把全部旧事件一概判错。
5. [rules.json](../../assets/resources/data/ming_end/rules.json) 属性范围 0–20，幼年开局范围 3–10；[presenters.ts](../../src/presenters.ts) 的 `formatWealth` 却统一加「两」，并用于局内、结算及部分选项成本。原制作方向已有家资抽象等级，当前「两」是表现偏差；不据此声称所有其他文字已查完。

## 二、当前可收集目录与历史档案分开

**决策：不为扩大收集范围新增原生书、碗起点，不批量造事件。**保留两张卡及所有原有成就、死因、链、事件的顶层 ID 和旧记录；不是从生产内容里删掉没收集的条目来制造满收集。图鉴将条目分成：

- **当前可收集**：逐条确认现行开局、条件、阶段、链、效果存在真实可走通路径后才列入当前目录；完成度的分子和分母都只来自这套目录。初始明确排除依赖书、碗的已知不可达成就；其他待查条目标为待核实，不宣称可达或静默计为已完成。零分母显示「暂无可收集条目」，不显示误导性的 100%。
- **历史档案**：原生不可达条目中已收集的，以及不在当前内容包但记录里存在的 ID，仍可查看为旧记录；能解析时显示现有名称，无法解析时明确「旧版条目，名称暂不可用」，保留原始 ID 用于追溯，不按当前目录计数。原生未收集条目保留在内容/维护清单中，图鉴可展示为「当前版本暂不可收集」，不能当已收集。

实施前产出**逐 ID 目录清单**：来源、是否历史收集、起点卡、条件/flag、事件与链路径、依赖的死因、目前状态及证据；同时核查 `AchievementHints.ts` 是否仍指向停用路径。不能只凭名称、字符串匹配卡 ID 或一次随机模拟就宣布全局可达；涉及 `any/not`、结算唯一主称号和多来源死因需逐分支判断。目录应由一处明确、可复核的维护清单或确定性规则提供，`CollectionProgress`、首页/结算数字和 `view.ts` 图鉴共同消费；内容变动后同步复核，不做运行时昂贵全图搜索。当前目录与历史两者的交集只计一次当前已收集，档案显示不重复领奖。

[01](01-玩法数值与人生节奏.md) 拟删除玉米`corn_store_risk`、`corn_relief_risk`，医药`delay`、`showoff`，手电`flashlight_claims`、`flashlight_misstep`及各自独占阶段；手电历史结伴核查、计算器自动黑屏误会的失败改为非致死小损失。实施时把受影响的专属死因、成就及对应提示、链节点、跨引用一起列入同一清单，六项新成就按01的替换表处理；死因若还有别的真实路径则仍可收集，不能只因删掉一个入口就排除。计算器成就含多个来源，不能把其中一条死亡路径停用等同于整个成就停用。

已核实部分 `A_MOD_*_DEATH_*` 的名称和短评明确描述死亡，不能沿用同一 ID 改成普通轶事，更不能把旧死亡记录解释成新奖。此类失去最后路径的条目保留原 ID 和原义，列为历史条目、移出当前可得分母，已收集者仍可查看，不自动补发。为保持每张现代卡当前目录十项，**仅对少数锁死奖做等数量替换**：用全新成就 ID，依据该卡已有且真实可达的非死亡里程碑，配置同稀有度的新奖；新旧奖独立统计，绝不把旧 ID 映射成新奖或自动授予。保留历史项与当前十项分开计算；若尚未找到合适的真实经历，暂不宣称该卡十项都可收集。新增成就不是新增事件或扩大原生起点，相关提示及引用须同步，不能把拟议变化当成已实施。

目录仅用项目现有数据和一处简明、明确的维护清单表达，不建设复杂目录系统；若决定为新旧状态或关联家当增加内容元数据，必须同步内容 schema、生成类型、加载/校验器及其调用，评估内容指纹和旧档影响，不能只在 JSON 加未被支持的字段。

## 三、图鉴与下一局：只做轻指引

继续保留成就/死因基本分类，增加简单的「家当」和「已收集 / 未收集」筛选；家当筛选依据条目已核实的关联卡，通用条目提供「全部/无特定家当」入口，不靠 ID 前缀生造关联。历史条目单独标识，不与当前完成度混算。允许玩家**可选一个目标**：只从当前可收集且有真实提示的条目选，显示家当与已核实的前置方向，例如「可带手电，留意夜巡相关经历」；不修改触发权重、不新增任务、进度条、奖励或必得承诺。目标收集后显示已达成并可清除/更换；版本变更后目标不可用时保留并提示「当前版本暂不可追」，允许清除，不自动换成别的。

目标是跨局偏好而非人生事实：若要持久化，单独存放本机偏好并验证读写，读取失败不阻塞人生、也不影响记录/传承；旧记录、只读状态不能因此被写坏。先复用既有展示数据与 `ACHIEVEMENT_HINTS`，仅展示已证实条件；提示本身不是调度保证，也不把旧名额或成就优先级规则说成必中。

## 四、传承与旧数据兼容

新奖励只提供五属性中任选一项开局 +1，受上限限制，仅下一局生效、不叠加；取消在**新传承选择页**把免费指定家当包装成奖励。普通免费换候选的功能不变。首页、传承页、身份页和结算提示同步修改，但不能把已有的旧选择当不存在。

按状态处理，先读记录和人生槽，再决定，不批量补发：

| 真实状态 | 后续方案 |
| --- | --- |
| 有可用资格、尚未预留 | 保留原资格，让玩家选一项属性 +1；取消返回不消耗。旧资格本身没有保存 `extra_card` 指定，不凭空认定选过哪张。 |
| 新旧界面中选了 `extra_card` 但尚未确认开局 | 当前 `selectedInheritance` 是内存状态，不宣称它已持久化；仍在同一会话的应保留所选并让玩家明确选择「按原方案继续」或「改选属性」，不静默替换。进程重启后若无持久证据，只恢复资格并提示重新选择，不伪造具体卡。 |
| claim 为 pending，匹配人生槽已确认 | 按现有 `lifeId` 核对并消耗一次；若该人生实际记载 `extra_card`，按旧语义保留该候选、可免费更换，不额外发属性，也不改写重放历史。 |
| pending 且能确定对应人生不存在 | 按现有 `reconcileInheritance` 释放预留，保留资格，再让玩家选择；若有独立可靠持久数据能证明确切旧选择，提供上述原方案/改选，否则不猜。 |
| pending 且损坏、恢复槽或不兼容导致不能确定 | 停止推进、保留原槽和 claim，提示先恢复并重新读取。仍无法恢复时，仅保留现行明确二次确认的永久放弃路径，说明不补发、不删除原人生槽，之后重开覆盖另行确认。不得自动释放、自动消耗或无条件补发。 |
| 已消耗资格或人生已开始 | 不补发、不把旧指定转成属性；只在旧人生可按现有规则读取时呈现其真实传承。 |

`extra_card` 的类型校验、存档解析与回放需要继续识别旧数据；隐藏新入口不等于把持久格式的旧枚举直接删除。`StaticContentLoader` 从真实内容计算指纹，`SaveCodec` 校验内容 ID、版本、指纹；本轮后若修改生产内容，**不绕过匹配、不伪改指纹**。不兼容的人生原槽保留、如实告知且重开单独确认；需要跨内容版本续玩时，必须先设计有证据、可验证的正式迁移或旧内容运行环境，不能承诺当前已有迁移。生命周期记录和人生槽分别检查，不因图鉴改动重置记录。

## 五、结算三段与逻辑补洞

### 三段回顾必须来自真实日志

使用 [EndingEvaluator.ts](../../src/game/core/engine/EndingEvaluator.ts) 的 `EndingReport`、实际日志/已聚合故事及 `player.cards`，按时间顺序选取三段：①开局身份和家当；②真实重要经历，优先玩家选择、事业进退或有结果的普通故事；③实际结局、死因与成就。段落只复述真实内容，不能把失败说成功，也不能凭家当编造事件。若某局没有选择或中途资料不足，第二段选真实普通经历；确实没有可证实材料则写「这段经历没有可展示的记录」，不凑故事。已完成人生简表仅存年龄、年数、成就、死因，无法凭它还原完整三段；旧档只呈现能证明的信息，不生成虚构细节。下局建议从真实未收集条目及现有可用家当选一个可做的方向，资料不足就不建议；不使用模型生成、不承诺必得。

### 幼龄和家庭先核事实，再改内容

开局可为 3 岁，逐一审查幼龄可能遇到的交易、外出、事业等事件及其选项、成功失败和后续阶段：符合儿童参与的行为可写成家人陪同/代办，效果与触发条件也要实际支持该叙述；确须成人独立承担的事件加真实年龄条件或寻找已有适配分支，不能只改「家人陪你」四个字掩盖状态不符。家人是否存在若没有事实字段，只说不虚构具体亲属的陪同者，或不使用该表述。

旧子女事件逐条追踪出生来源、年份/年龄组、存活及成长前提：出生不等于活着；成年、婚嫁、孙辈都必须有足够的出生时间和存活事实。能用现有标记表达的加条件并对照所有分支；旧 `F_LIFE_HAS_CHILD` 无法确定年龄/性别/存活时不臆测，用已有承接事件建立可证明事实后才进入具体成长情节，或保守不触发具体叙事，不能造一个更早的生日。若现有状态无法准确表达，先设计最小记录和旧档兼容，再修改，禁止伪造旧经历。核对死亡后不再参加长大/婚嫁事件，多名子女不能因一人死亡误判全部死亡；这不是新增复杂家庭资源系统。

### 家资统一为抽象刻度

保留 0–20 数值、条件和效果，不新设货币、物价或经济系统。把 `formatWealth` 改为无「两」的刻度显示，如「家资 3」；属性变化与成本、收益统一写「家资 +1 / -1」，同一局内、卡/链承诺、事件、选项、日志、图鉴提示和结算都按同一含义核对。具体某笔交易的自然叙事可以提银钱，但不能把数值点直接解释成一两银子；同步检查 `EnumMapper`、`LogParser` 和生产文案，不只改一个函数。实际效果受 0–20 截断，提示不能把名义变化误写成必得数额。纯展示修改与内容字段修改分开评估，后者触发内容指纹变化。

## 六、实施顺序与轻验收

1. 先逐 ID 梳理书碗与拟删菜单的依赖，形成当前目录/历史档案及成就条件对照；再调整 `CollectionProgress.ts`、`LifetimeRecords.ts` 快照、`controller.ts`、`view.ts` 与 `AchievementHints.ts` 的一致呈现。保留旧记录，不批量生成事件。
2. 先设计传承各状态与回放兼容，再收起新 `extra_card` 入口；对存档指纹、失败阻断和二次确认单独核对。随后用真实日志做结算回顾，最后逐事件修幼龄/子女因果并统一家资单位。
3. 验收覆盖：书碗不可达但历史已收集仍在；当前分母不含停用项；有其他路径的死因仍可收集；目标可选可取消且无奖励；新/旧资格、匹配/确定不存在/不确定 pending、损坏及不兼容槽均不吞记录或重复发放；真实回顾缺素材不编造；幼年、子女死亡与成长互斥；家资成本收益不把数值点写成「两」。内容变动按仓库规范校验及测试，Web/微信分别检查实际界面；具体检查结果以 [README](../../README.md) 的记录为准，未检查的平台不得宣称通过。
